# Правила ведения документации — cv-air

## Структура

```
docs/
├── README.md                   ← корень, ссылки только на дочерние README
├── CONTRIBUTING.md             ← этот файл
├── project/                    ← техническая документация
│   ├── README.md               ← индекс, ссылки на все файлы папки
│   ├── pages.md                ← маршруты, getStaticPaths, SEO, sitemap
│   ├── components.md           ← компоненты v1/v2, layouts, props
│   ├── content.md              ← i18n-бандлы, types/cv.ts, слой сервисов
│   ├── logic.md                ← consts.ts, хелперы v2, клиентские скрипты
│   ├── design.md               ← два набора токенов, шрифты, Tailwind-мост
│   ├── resume.md               ← A4-документ /resume: пагинация, печать, ATS
│   └── deploy.md               ← сборка, статический вывод, хостинг
└── changes/                    ← история изменений
    ├── README.md               ← индекс, ссылки на папки месяцев
    └── YYYY-MM/                ← папка месяца
        ├── README.md           ← индекс, ссылки на файлы дней
        └── YYYY-MM-DD.md       ← изменения за день
```

## Правило связей — дерево

Ссылки между файлами документации идут **только сверху вниз**: родитель → ребенок.

- `docs/README.md` ссылается на `project/README.md` и `changes/README.md`
- `project/README.md` ссылается на `pages.md`, `components.md`, ...
- `changes/README.md` ссылается на `2026-08/README.md`, `2026-07/README.md`
- `2026-08/README.md` ссылается на `2026-08-03.md`, `2026-08-01.md`, ...

**Запрещено:**

- Обратные ссылки (ребенок → родитель)
- Перекрестные ссылки (сосед → сосед, например `pages.md` → `components.md`)
- Ссылки через уровни (корень → leaf, минуя промежуточный README)

**Формат ссылок:** `[текст](файл.md)` — стандартный markdown, не wiki-links.

Ссылки на исходники (`src/i18n/en.ts`, `astro.config.mjs`) под это правило **не подпадают** —
это не документация. Ставить их можно из любого файла и нужно как можно чаще: документ
описывает поведение, код остается источником правды.

## Навигация для ИИ-агентов

Агент всегда стартует с `docs/README.md` и спускается по дереву:

```
docs/README.md → project/README.md → нужный файл
docs/README.md → changes/README.md → YYYY-MM/README.md → нужный день
```

Максимум 3 шага до любого файла.

## Границы: CLAUDE.md, DESIGN.md, docs/

Три источника, которые нельзя смешивать:

| Файл         | Что в нем                                                              |
| ------------ | ---------------------------------------------------------------------- |
| `CLAUDE.md`  | Правила работы с репозиторием: команды, инварианты, чего не делать      |
| `DESIGN.md`  | Дизайн-система: философия, палитра, типографика, моушен, «дон'ты»       |
| `docs/`      | Карта проекта: что где лежит, как устроено, как расширять               |

`docs/` **не переписывает** первые два. Если факт уже есть в `CLAUDE.md` или `DESIGN.md` —
в `docs/` идет одна строка со ссылкой на этот файл, а не копия абзаца.

## Когда обновлять docs

**После структурных изменений** — обновить соответствующий файл в `project/`:

- Новый/удаленный маршрут, изменение `getStaticPaths`, canonical/hreflang, фильтр sitemap → `pages.md`
- Новый/измененный компонент или layout, изменение props → `components.md`
- Новое поле в `types/cv.ts`, новый сервис, новая локаль → `content.md`
- Новый хелпер в `v2/ui.ts`, изменение `consts.ts`, правка инлайн-скриптов → `logic.md`
- Новый токен, смена шрифта, правка `tailwind.config.ts` → `design.md`
- Изменение верстки, пагинации или печати A4-резюме → `resume.md`
- Изменение сборки, вывода, хостинга → `deploy.md`

**После неочевидных изменений поведения** — создать файл в `changes/`:

1. Определить месяц: `changes/YYYY-MM/`
2. Если папки месяца нет — создать с `README.md`
3. Создать файл `YYYY-MM-DD.md`
4. Добавить ссылку на него в `changes/YYYY-MM/README.md`

Неочевидное — это то, что нельзя вывести из чтения кода: почему выбран обходной путь,
что сломалось и как это диагностировали, какое поведение зависит от порядка/времени
(pre-paint, пагинация после `document.fonts.ready`, гидрация которой нет).

## Как добавить запись в changes

### 1. Создать файл дня

Файл: `docs/changes/YYYY-MM/YYYY-MM-DD.md`

```markdown
# [YYYY-MM-DD] Краткое описание

### Что изменено

- ...

### Затронутые файлы

- ...

### Как вернуть

...
```

Если за день несколько изменений — объединить в один файл с разделителями `---`.

### 2. Добавить ссылку в README месяца

Файл: `docs/changes/YYYY-MM/README.md`

```markdown
# Месяц YYYY

| Дата | Файл                           | Описание         |
| ---- | ------------------------------ | ---------------- |
| DD   | [YYYY-MM-DD.md](YYYY-MM-DD.md) | Краткое описание |
```

### 3. Если месяц новый — добавить в `changes/README.md`

```markdown
| [Месяц YYYY](YYYY-MM/README.md) | Краткое описание |
```

## Как добавить файл в project/

1. Создать файл в `docs/project/`
2. Добавить ссылку на него в `docs/project/README.md`
3. **Не** добавлять ссылки из других файлов на новый

## Формат файлов в project/

- Первая строка — `# Заголовок`, вторая — одно предложение о зоне ответственности файла.
- Пути к исходникам — инлайн-кодом (`src/services/index.ts`), а не абстрактными описаниями.
- Таблицы для перечислений (маршруты, компоненты, токены), списки — для правил.
- Инварианты формулировать как запрет с причиной: «не импортировать `i18n` в компонентах —
  ломается однонаправленный поток контента», а не «желательно использовать сервисы».

## Что НЕ документировать

- Информация, которую можно получить из кода (`git log`, `git blame`, чтение файлов)
- Временные заметки и in-progress задачи
- Дублирование содержимого `CLAUDE.md` и `DESIGN.md`
- Тексты CV: они живут в `src/i18n/{en,ru,uz}.ts` и меняются чаще документации
